#### By day 10: pull-based inference pool

Workers check out jobs; the server never pushes. Design in five pieces:

1. **Queue on the main server** (Rust, new table or JSON store): jobs have `id`, `task`, `payload` (image ref or capture id), `requirements` (min VRAM, model), `state` (`queued → leased → done/failed`), `lease_until`, `attempts`.

The recipient (your age *public* key, `age1...` — safe to store anywhere) goes in `.sops.yaml`. Scripts then call bare `sops encrypt` / `sops decrypt` with no flags:

```sh
cat > ~/.sops.yaml <<'EOF'
creation_rules:

```

Replace the placeholder with the `age1...` line from your `age-keygen` output (the public half — never the `AGE-SECRET-KEY-...` half, which stays only in `~/.config/sops/age/keys.txt` at 600).

```sh
sops encrypt -i ~/.huggingface.env     # encrypts in place, recipient from the yaml
eval "$(sops decrypt ~/.huggingface.env)"  # use in scripts
```

How it resolves: `sops` walks up from the target file to find the nearest `.sops.yaml`, matches `path_regex`, and uses that rule's recipient. So future scripts need zero key handling — just `sops decrypt <file>`.

Two details worth knowing:

- **Scope**: `~/.sops.yaml` in home covers everything under home. If you later want different recipients per directory (e.g. one key for tokens, another for pool worker keys), drop additional `.sops.yaml` files in those directories — nearest wins.
- **Key discovery**: decryption finds your secret key automatically at `~/.config/sops/age/keys.txt`. If you ever move it, point `SOPS_AGE_KEY_FILE` at the new path (that variable may itself live in your shell rc — it names a file, not a secret).
